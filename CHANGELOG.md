# Changelog

## Unreleased

- **Admin permissions team id is now the constant `Admin::PERMISSIONS_TEAM_ID` = `0` (breaking for existing installs).** Admin role assignments used to live under the config key `admin_permissions_team_id` (`1`), which needed a placeholder tenant to own that id. The key is gone (remove it from published configs); `0` is a value no tenant can have, so the placeholder tenant is no longer needed (delete it from existing installs by hand). Fresh installs need nothing; an existing install moves its admin `model_has_roles` / `model_has_permissions` rows to `0` by hand. `DeleteTenantPermissionData` now only deletes tenant user pivot rows (by `model_type`) and tenant guard roles, so deleting a tenant can never touch admin rows.
- **Tenant cancellation and deletion are event driven.** `CancelTenant` only marks the tenant and dispatches `TenantCancelled`; `DeleteTenant` dispatches `TenantDeleting` inside its transaction, then removes the members and the permission rows itself (`Actions\Tenant\{DeleteTenantMembers,DeleteTenantPermissionData}`, core, always) and deletes the tenant row. Whatever owns data reacts to the events with a listener that calls reusable action classes: the package's general `CancelledTenant` / `DeletedTenant` listeners run its own actions (`Actions\Invitation\{RevokePendingInvitations,DeleteTenantInvitations}`, only with `features.invitations`), and the application adds its own general listeners in `app/Listeners/Tenant` (`RegisteredTenant`, `CancelledTenant`, `ReactivatedTenant`, `DeletedTenant`, one per lifecycle event, empty `actions()` by default), which Laravel discovers (publish starting points with `php artisan vendor:publish --tag=tenancy-foundation-stubs`; the template's `DeletedTenant` lists `DeleteSubscriptionData` and `DeleteTenantAddresses`). Listeners run while the tenant and its members still exist; a failing one rolls the deletion back. The `RoleObserver` calls `Actions\Invitation\ReleaseRoleInvitations`. Apps that kept their own `TenantDeleting` listener keep working unchanged.
- **Invitations moved into the package (backend), behind `features.invitations` (default `true`).** New: `Models\Invitation` (`models.invitation`), `InvitationFactory`, migration `create_invitations_table` (always runs, even with the flag off, so the schema never depends on a feature flag; skipped only when the table exists; `invited_by` is nullable; `role_id` has no foreign key so migration order against the permission tables does not matter, the `RoleObserver` clears it when a role is deleted), `Actions\Invitation\{CreateInvitation,AcceptInvitation}`, `InvitationIssued` + `SendInvitationNotification`, `Notifications\InvitationCreated` (`notifications.invitation_created`, `null` disables), `InvitationPermissions` (seeded by `TenantRolePermissionsSeeder`: admin all, view only view/view_any), `Policies\Tenant\InvitationPolicy`, `RoleObserver` (cancels pending invitations of a deleted role), pruning of expired invitations, and `CancelTenant` / `DeleteTenant` clean up the tenant's invitations. Expiry and retention are `invitations.expiry_days` / `invitations.retention_days` (add the `features`, `invitations` and `models.invitation` keys to published configs). The invitations resource (list, "Invite user" modal, revoke; `InvitationResource`, `usingInvitationResource()`, only with the flag on) lives in the package too: the form's roles are the assignable tenant roles, the table shows the inviter through the configured name attributes, and an `InvalidInvitation` (member already, owner role) becomes a notification. The accept page and its signed route (`invitations.accept`) are registered by `TenantPlugin` (`usingAcceptInvitationPage()`, only with the flag on); the mail link comes from `AcceptInvitation::routeName()` instead of a hardcoded app route, and the form uses the configured name attributes. Apps delete their own copies (accept page, `->routes(...)` call in the panel provider) and keep `App\Models\Invitation extends` the package model. `AcceptInvitation` re-checks under a row lock that the invitation is still pending (accepted, expired and deleted-account cases throw `Exceptions\InvalidInvitation`), verifies the email of a new user and dispatches `InvitationAccepted` after commit. `CreateInvitation` takes a nullable inviter, refuses the owner role and current members, and the invitation hides its `token`.
- "Send password reset link" is also a row action on the admin portal users table and the tenant Users relation manager; it is hidden for deleted users and, on both reset actions (users and admins), for your own row.
- Verified (email) icon column on the admin portal users, admin users, tenant users relation manager and tenant panel users tables (`Components\Tables\Columns\VerifiedColumn`, sortable). A matching verified filter (Filament's default Yes/No/All ternary) is on the same tables.
- `RedirectDeletedUserHome` (tenant panel, persistent): a user whose session is still signed in but whose account was deleted is sent to `app.url` and the session is cleared, instead of landing on a login redirect on the tenant subdomain.
- Soft deleted users in the tenant users table only offer restore and force delete: edit (shared `UsersTable`, so the admin users table too), make owner, remove ownership and remove from tenant are hidden for trashed records.
- Email change verification is on for both panels (`email_change_verification`, default `true`; `false` saves profile email changes directly). The old email stays until the link sent to the new address is used (valid one hour, marks the email verified); the old address gets a notice with a block link. Add the key to published configs.

- Tenant panel user edit form (same layout as the admin forms: details and access sections, read-only status sidebar). Owners and admins with `user.update` change the name and the tenant roles (`Actions\Tenant\UpdateTenantUser`, owner role excluded via `TenantRoles::assignableOptions()`). The email is read-only; the roles section is hidden for owners and yourself; a user who belongs to other tenants keeps their name (read-only). Create is unchanged until the Phase 4 invite flow.
- **Breaking:** the tenant profile page now lives at `/tenant-profile` (slug `tenant-profile`). It shared `/profile` with the user profile, so on a tenant domain the navbar profile link opened the tenant profile instead of the user profile.

- Admins have a `status` (`pending`, `active`, `inactive`) instead of an `active` flag (fresh migrate needed). Only pending and active, non soft deleted admins pass `canAccessPanel()`; a pending admin has a random password and becomes active, with the email marked verified, when the password reset link is used (`ActivateAdminOnPasswordReset`).
- Password reset enabled on both panels. Admins use their own `admin_password_reset_tokens` table (new migration) so tokens never cross between an admin and a tenant user sharing an email.
- Admin users resource (`AdminUserResource`, slug `admins`, `usingAdminUserResource()`): list, view, edit and create. Creating an admin stores a random password with status `pending`, dispatches `AdminUserCreated` and queues the `AdminInvited` email with a set password link (`notifications.admin_invited`, `null` disables it). Admins cannot delete themselves or the last active super admin. The table filters by role, status and trashed, with delete, restore and force delete (force delete is super admin only).
- Admin user actions on the table (action group) and view/edit headers: activate, deactivate (status guarded, clears the remember token; self and the last active super admin are refused), send password reset link (non pending admins), change role (`ChangeAdminUserRole`, shared with the edit form). `AdminPolicy` has `activate`, `deactivate`, `changeRole` and `sendPasswordResetLink`, all guarded by `admin_user.update` and super admin protection.
- Support role can view admins (`admin_user.view_any`, `admin_user.view`; re-run `AdminRolePermissionsSeeder`). An email that belongs to a soft deleted admin gets a message pointing to restoring it instead of the generic taken error.
- **Breaking:** the `filament-defaults` Edit, View, Delete, Restore and Force delete actions are no longer icon buttons; they keep their icon and show their label (page headers need no `button()->hiddenLabel(false)->tooltip(null)` override any more). All package tables now put row actions in one `ActionGroup`; the shared `UsersTable` exposes `rowActions()` instead of `recordActions()` for subclasses.
- The admin edit form has no role section any more (role is set on create and changed with the Change role action); `UpdateAdminUser::handle()` no longer takes an actor or a role.
- The public contact page moved into the package: route `public.contact` (`contact_requests.public_path`, default `contact`, `null` disables; registered on `domain` only), view `tenancy-foundation::contact` on Filament's simple layout, and `contact_requests.public_form` to swap the Livewire component. `PublicContactForm` has a `fields()` hook. Apps can delete their own `/contact` route and `contact` view.
- **Breaking:** Action classes moved into folders: `Actions\Admin` (`ChangeAdminUserRole`, `ChangeAdminUserStatus`, `CreateAdminUser`, `InviteAdminUser`, `SendAdminPasswordResetLink`, `UpdateAdminUser`), `Actions\Tenant` (`CancelTenant`, `CreateTenant`, `DeleteTenant`, `ReactivateTenant`, `RegisterTenantOwner`, `TransferTenantOwnership`), `Actions\Roles` (`AssignTenantRole`) and `Actions\Contact` (`ChangeContactRequestStatus`, `CreateContactRequest`, `RespondToContactRequest`). Update any `use` statements in your app.
- Admin portal tenant users: the create page is gone; new `ViewUser` page, `UserInfolist` (details plus status sidebar: account state, tenant count, last login and IP, email verified, created) and a real `UserForm` (name attributes, unique email with a restore hint for deleted users) with `mainComponents()`, `sideComponents()`, `detailsFields()` hooks. The shared `UserResource` base now has `getRecordTitle()`.
- Admin portal user pages have a Tenants relation manager (`TenantsRelationManager`, `UserTenantsTable`): tenant, subdomain, role in that tenant (`UserTenantRoles`), owner flag, joined, status. Row actions in a group: open tenant, make owner (`TransferTenantOwnership::handleAsAdministrator()`), change role (`AssignTenantRole`); both need `user.update`. The tab needs permission to view tenants. Remove from tenant comes with `RemoveTenantMember` in Phase 4.
- Admin portal user header actions (view and edit pages): impersonate, send password reset link, mark email verified, plus edit, delete, restore, force delete. New permission `user.send_password_reset` (Support and Admin get it; re-run `AdminRolePermissionsSeeder`); marking verified needs `user.update`. The reset email logic is now the generic `Actions\Auth\SendPasswordResetLink` (replaces `Actions\Admin\SendAdminPasswordResetLink`). The sole owner delete refusal names the tenants (`User::soleOwnedTenants()`).
- Admin portal: "Manage roles" (`ManageTenantRolesAction`, `SyncTenantRoles`) sets several tenant roles for a user, from both the tenant Users tab and the user Tenants tab. It needs `user.update` (super admin and admin, not support), is hidden on owner rows and keeps the owner role of owners. It replaces the single role "Change role" on the user Tenants tab (`ChangeUserTenantRoleAction` removed).
- **Multiple owners per tenant.** "Make owner" now adds an owner (`Actions\Tenant\AddTenantOwner`) instead of transferring; new "Remove ownership" (`RemoveTenantOwner`) demotes an owner to admin. Any owner can add or remove owners in the tenant panel, and admins with `user.update` can in the admin portal (Tenants tab and tenant Users tab). A tenant always keeps at least one owner: the last owner cannot be removed, by anyone. `TransferTenantOwnership` stays for a full hand over. Cancellation and reactivation emails already go to every owner.
- Admin portal: "Remove from tenant" (`Actions\Tenant\RemoveTenantMember`, `RemoveUserFromTenantAction`) on the user Tenants tab and the tenant Users tab. Only for users in more than one tenant, never for an owner of that tenant; it detaches the user, clears their roles in that tenant and moves the default tenant flag if needed. Needs `user.update`.
- Row actions for owners and removal avoid per-row queries (owner and tenant counts are eager loaded or cached per request; the tenant panel users table also eager loads `tenants`). `RowActionQueryCountTest` guards the two admin tabs and the tenant panel list.
- Tenant panel users: "Remove from tenant" (`RemoveFromTenantAction`, policy ability `removeMember` via `user.delete`) for members who belong to other tenants; never for an owner of the tenant or yourself. A user who belongs to other tenants can no longer be deleted or force deleted from the tenant panel (`TenantMembershipGuard` in the tenant `Gate::before`, so owners are covered and bulk delete skips them); a user in only this tenant is deleted (soft delete) as before.
- A reset or invitation link that is invalid, expired or replaced by a newer one now sends the visitor to the request password reset page with a message, instead of showing the form first (`Filament\Pages\ResetPassword`, both panels).
- `profile()` on both panels (`EditProfile`, `usingProfilePage()` on both plugins); shared `UserNameSchema`.
- `User::isOwner()` reads the `tenant_user.is_owner` flag and drives the owner `Gate::before`, which returns `null` for non owners. New `tenant_user (tenant_id, is_owner)` index in the tenants migration (fresh migrate needed).
- The tenant profile page (General, Billing and Cancel account tabs in the app) is owner only. The seeder gives the Owner role no permission rows (it bypasses checks); re-run the seeders.

- Initial extraction: models, concerns, enums, middleware, policies, Filament components, user resources, tenancy pages, panel plugins, Filament defaults, migrations, seeders, factories, responses, install command.
